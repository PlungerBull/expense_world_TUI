# Runtime Behavior

How the app (`expense`, the TUI) and the sheet import (`expense import sheet`) behave at runtime — read/write semantics, error handling, working against the live engine. Companions: [tui.md](tui.md) (the app) and [commands.md](commands.md) (the sheet import and the settings file).

## Overview

The client holds no business logic and **no local state beyond `~/.expense-config`** — no cache, no offline write queue ([decisions.md](decisions.md) "All reads are live"). The engine is the only authoritative store and runs on the same machine (`http://127.0.0.1:8000`), so every read is a live loopback HTTP call.

Everything here applies equally to the TUI (`expense`) and the sheet import (`expense import sheet`): they are clients of the same HTTP client and `fetch_*` functions, not separate runtimes.

## The settings file and a fresh start

The engine address and key live in the settings file, `~/.expense-config` (or the path `EXPENSE_CONFIG` names; its fields are in [commands.md](commands.md)). [expense/config.py](../expense/config.py) is its one reader and writer: `save` writes a temp file beside it, sets it to chmod 600 and moves it into place.

**A fresh start needs no command.** When the app opens and there is no settings file it can use — none at all, or one that cannot be read (damaged or half-written JSON, a body that is not a config, bytes that are not text, a path it may not read: `config.load_usable`) — it opens on its setup screen, which asks for the engine address (offered as the local engine's, `http://127.0.0.1:8000`) and the key, and for a name when the engine has no profile for that key ([tui.md](tui.md) §2 "Setup comes first"). Nothing is written until the engine has accepted the address and key and the profile exists; then the file is saved, replacing a damaged one. `expense import sheet`, finding no usable file, stops on every step with a message pointing at the app's setup screen (exit 3).

## Read semantics

Every read is a direct `GET`. What a screen shows is what the engine computed at that moment, including home-currency figures (converted engine-side at read time).

- The engine's responses are IDs-only; the screens resolve names through live reference-list reads (`load_*_name_map` in [expense/reads.py](../expense/reads.py)), with a short-id fallback when one fails.
- **Deleted is deleted.** A deleted row is invisible to every client — no list returns it, its get is a 404 — and nothing in the app restores it. The engine keeps the row in its table; undeleting is an operator task outside the API (contract: "Base Conventions", "A delete is final"). The engine's activity history still holds a deleted row's history; this client has no screen for it.
- Transaction reads always send `debit_as_negative=true`, so the request pins the sign rather than depending on the engine default. The bank upload's rows and their days' unclaimed parts (contract: POST /v1/transactions/import) and a bank line's parts (contract: GET /v1/bank-lines/{bank_line_id}) arrive unsigned, as a magnitude and a `transaction_type`; `signed_cents` in [expense/formatting.py](../expense/formatting.py) signs them, the one place the app reads the sign off the type.

### Three list shapes

No list pages by position; every list is one of three shapes, each read its own way. The rules are the engine's (contract: "Base Conventions", "Lists come in three shapes, and none of them is paged by position"), with (contract: "Base Conventions", "Cursors, on every cursor-paged list") and (contract: "Base Conventions", "Date windows").

| Shape | Lists | How the app reads it |
|---|---|---|
| **Whole** `{items}` | accounts, categories, hashtags, a category's hashtags, one account's reconciliations | One read, every row; no paging parameters. |
| **Cursor** `{items, limit, next_cursor}` | transactions, bank lines | `?after=<next_cursor>` until it is `null`. A count is its own read, once per list, for the lists that show one: `/transactions/count` for the ledger, `/bank-lines/count` for the reconciliation's "no batch" list; the reconciliation tick-list reads every page and no count. The TUI's growing lists are [tui.md](tui.md) §5. |
| **Cursor + date window** | activity, exchange-rate history | The cursor inside one window (30 calendar days counting `date_to`'s own day when `date_from` is left out; at most 366, counting both ends). The window before it is read by sending the response's `previous_date_to` back unchanged as `date_to`, which reads no row twice; `null` means nothing earlier. No screen reads these. |

A stale `limit`, `offset` or unknown parameter is the engine's `422`, never a quietly wrong answer.

## Write semantics

Writes go straight to the engine the moment you press enter. There is **no offline write queue, no buffering, no replay**.

- Each write carries an `X-Idempotency-Key` (UUID) minted once per logical write by `ExpenseClient`; retrying is safe — the engine returns the original response. Keys are **permanent** (no TTL). Replay requires the *same* request: each key stores a fingerprint over method/path/query/body, and reusing a key with a different body returns `409`.
- `ExpenseClient` retries a timed-out or 5xx write up to twice (1s/2s backoff) **with the same key** before surfacing the error, printing a stderr notice per attempt. Connect failures are not retried, and reads never auto-retry.
- Any other network error fails fast: the app shows it and the sheet import prints it and exits non-zero, so nothing assumes a write landed that did not.

**Bulk writes** go through one shared path, [expense/batch_write.py](../expense/batch_write.py), used by the TUI's LOG bar (`ctrl+s`). Rows go out in chunked `POST /transactions/batch` calls of 200 rows by default, each with its own idempotency key. The engine takes at most 500 rows in one request (contract: POST /v1/transactions/batch); `ENGINE_BATCH_MAX` in that module is the limit's one home in the code, and a chunk size outside 1–500 is refused before anything is sent. A batch is **atomic** — one bad row and none of the chunk is written (contract: POST /v1/transactions/batch, "No partial success") — but a refusal names **every** row of the step that refused it, each keyed `transactions.<i>.<field>` by its place in the request (contract: POST /v1/transactions/batch). So one refused send settles every row it names, and the rows it does not name go again as one batch, with a new idempotency key since the body differs, until a send lands or no row is left: a chunk costs one request, plus one for each send that drops rows. A row refused only because its own id is taken is **not** a failure: ids are client-supplied, and a create sent again answers `ID_EXISTS` on its own id before any other refusal (contract: "Base Conventions", "Which refusal comes first on a create"), so `ID_EXISTS` on `transactions.<i>.id` and nothing else on that row means the row is already in. That is what makes a retry after a half-written save safe, at one request per chunk, plus one for a chunk mixing landed and new rows. Every other refusal of a row (a zero amount, a taken operation code, a sealed period) fails that row in the engine's words for it, keyed by the field alone (`amount_cents: Must not be zero.`), since its place in a send is not its place in the list (`errors.is_own_id_replay` in [expense/errors.py](../expense/errors.py)). Items sharing a `line_group` are the parts of one bank line, whose ledger refusals the engine names on the first item (contract: POST /v1/transactions/batch, "Line groups"): a chunk never cuts a group (a group that does not fit starts the next chunk, and one longer than the chunk size is a chunk of its own), and a refused part fails every part of its group, so no line lands with a part missing. A refusal that names no row — a `401`, `403` or `5xx`, or a `409`/`422` with a key that is no item of the send (`transactions` itself, `category_id`, `X-Idempotency-Key`) — fails every unsettled row of the chunk alike, so it is reported once for the chunk, not sent again; later chunks still go. **Two refusals stop the run**, because every further write would draw them too (`refuses_every_write` in [expense/errors.py](../expense/errors.py)): nothing more is sent, and the rows not yet settled stay unsent. `SETTINGS_MISSING` is a `422`, but about the account and not about any row (matched on the error code alone), so its chunk's unsettled rows are failed as one group. `LIMIT_REACHED` with `LINE_CODES_EXHAUSTED` (matched on the code and that reason) means every line code up to `#999999` has been given, so no create that needs a new bank line can land again (contract: "Transactions (Ledger)", "Bank lines"); it names the first item that needed a new line, `transactions.<i>.id` (contract: POST /v1/transactions/batch, "Line groups"), and that row, with its group, fails in the engine's words for it. Every run of several writes follows the same rule — the first such refusal ends it and is shown once: the LOG bar shows it as one toast, in the engine's words with its hint if it has one ("Engine errors surface cleanly" below), and puts it on no row, while a row refused for its own reason earlier in the save keeps that refusal; a TUI bulk edit sends no further row and says it in the LOG bar's note (its `PUT`s make no new line, so only `SETTINGS_MISSING` reaches it).

**How refused rows read**, under the LOG bar's table and in the ledger's bulk-edit toasts alike, through one shared grouping (`grouped_refusals` in [expense/formatting.py](../expense/formatting.py)): one line per kind of refusal, what was refused, then the rows it hit (`row 77`, or `rows 3, 5, 7` for several). A row the engine names shows each refused field's name, as the engine keys it with the row's place in the request taken off, then the engine's words for it (`errors.row_words`); a row refused on two fields joins the pairs with ` · ` (`amount_cents: Must not be zero. · date: Must not be null.`), and a refusal naming no field shows its message. Rows refused alike share one line, whichever send of the run refused them: alike is the same code, fields and reasons as the row reads them (`errors.refusal_kind`, which `BatchFailure.kind` in [batch_write.py](../expense/batch_write.py) reads), never the top-level message, which counts the items a send named. A refusal naming no row is a line of its own, never joined to another: the engine's words whole, the rows it covers after its first line, its field lines under it. What each surface adds: [tui.md](tui.md) "Refused rows read one line per kind of error". The sheet import's refused rows go through the same grouping, keyed by their spreadsheet row ([commands.md](commands.md) "A sheet with bad rows").

## Engine errors surface cleanly

The engine's `{ error: { code, message, fields, reasons } }` envelope is rendered intact (format in [commands.md](commands.md) "Output conventions"); `expense import sheet --json` prints it verbatim. `EngineError` ([expense/errors.py](../expense/errors.py)) keeps `reasons` — each refused field's reason code (contract: "Error reasons"), `None` when the engine sends it null or leaves it out — for code to decide on. The app may add a line for a known refusal without replacing the engine's message; it is chosen by the error code and the reason code, never by the route or the wording of `message` or `fields` ([decisions.md](decisions.md) "Hints are chosen by the engine's reasons, never its wording"). Which refusals get a line, and the lines themselves, are listed in [tui.md](tui.md) "When the engine says no". The sheet import prints the engine's words alone, with none of the app's lines (`engine_text` in [expense/errors.py](../expense/errors.py)). The `--json` envelope the sheet import composes itself (`CONNECTION_ERROR`, `CONFIG_*`, and `NAMES_MISSING` for an `--apply` with a name missing: [commands.md](commands.md) "Sanctioned exceptions") has the same four keys, with `fields` and `reasons` null (`errors.error_envelope`).

Two hints belong to no single screen and live in the shared error text, `format_error` in [expense/errors.py](../expense/errors.py), which the TUI's toasts and banners print. Every screen that reports an engine error through that text shows them after a blank line under the engine's code, message and fields; the TUI bank import shows them in its toast, its on-screen refusal being the code, the message and a line per refused key ([tui.md](tui.md) "The import door"):

- **A `401`** — the key is missing or not valid: `Hint: the key is missing or not valid. Set a fresh one on System ▸ Config (press t).`
- **`SETTINGS_MISSING`** — the user's settings do not exist yet (contract: "Error codes"). Both rate reads list it among the codes they can return (contract: GET /v1/exchange-rates) (contract: GET /v1/exchange-rates/history). Matched on the error code alone: `Hint: First-time setup is not done yet. Open System ▸ Auth & profile and press b.`

Every remedy the shared text gives points at a screen of the app, never at a typed command (guard: `test_no_message_in_the_app_tells_the_owner_to_type_a_command` in [tests/unit/test_tui_setup.py](../tests/unit/test_tui_setup.py)).

Neither reaches `--json`, which stays the engine's body. The TUI's launch-time rate check shows nothing on any engine error, this one included.

## Working against the live engine

There is exactly **one engine: the local deployment** (`http://127.0.0.1:8000`, launchd service on the owner's Mac, set up by the engine's local-deployment guide). No staging, no sandbox — every PAT belongs to a real user and every write lands in the one true ledger.

**Developer default is live.** A plain `expense` (the app) or `expense import sheet` reads `~/.expense-config` — the real credential. Reads are safe; ad-hoc writes are real writes. To inspect behaviour, use the unit suite.

**Isolation levers, weakest to strongest:**

- `EXPENSE_CONFIG` redirects the config file. This isolates *local config only* — the same PAT still writes to the same ledger.
- A **separate PAT for a separate user** is data isolation within the same database (PATs: [commands.md](commands.md) "Auth model").
- **A second engine over the `expense_world_test` database** — how the contract suite runs. Nothing it writes can reach the real ledger, and the engine's test-database script, run with `--force`, wipes it.

  **Start and stop it with one command, from this repo:** `scripts/practice-engine up` and `scripts/practice-engine down` ([scripts/practice-engine](../scripts/practice-engine)). Every agent may run them; the orchestrator does, before and after a task that needs the contract live. `up` starts the engine exactly as below (or reuses the one already on `:8002`), waits for `/health`, reseeds the two practice users and prints their fresh keys to the terminal. `down` stops whatever listens on `:8002` when its command line is the practice engine's start (`-m uvicorn app.main:app --port 8002`), whoever started it, a tester's hand start included; anything else on the port is left alone. The script fixes the port, the database and the interpreter itself, takes no options, and runs everything under a fixed environment (`bash -p`, every inherited variable unset, `env -i` with only `HOME`, `USER`, `LOGNAME` and `PATH=/usr/bin:/bin:/usr/sbin:/sbin`), so nothing the caller sets reaches the engine or the reseed. The session guard ([.claude/hooks/guard.py](../.claude/hooks/guard.py)) lets a command that names the script through only when the whole command is `scripts/practice-engine up` or `scripts/practice-engine down`, optionally followed by `> /dev/null`, `2>&1` or one pipe into a plain `sed`/`grep`/`head`/`tail` filter: no chaining, grouping, substitution, env prefix or wrapper, so its output, which carries both keys, reaches only the terminal; its docstring lists the exact shapes and what it cannot see. The rest of this item is what the script runs, and what the tester may still run by hand.

  In the engine repo, `deploy/local/seed-test-user.sh` seeds two practice users, a PAT for each and a copy of `exchange_rates`. The **shared practice user** is the one every contract test writes as. The **reserved-names practice user** owns categories named `@Pendiente` and `@Opening` and a hashtag named `Pendiente`, holding the reserved names, so a test can draw the engine's refusal of a reserved name as that user. `--force` reseeds: it revokes every PAT each practice user holds, prints one fresh one per user, each under its user's heading (`shared practice user (<id>):`, then `reserved-names practice user (<id>):`), and refreshes the copy of `exchange_rates`; each practice user's id and every row it holds stay, so a test cleans up the rows it makes and never assumes a practice user starts empty. Run it from the engine checkout. The guard refuses the start with any other interpreter (`python`, `python3`, this repo's own venv, any other path). `-m uvicorn` is how the engine's own local setup starts it, not the console script.   **A start that crashes may be the engine mid-edit.** The engine checkout's working tree can hold a half-written change, and the engine starts from the working tree, not from its last commit. When the engine fails to start, ask the owner whether the engine coders have unfinished work before writing an engine ask.

  **Port 8002, not 8001.** `:8001` is `todo_world_engine`'s — point the suite there and every request 404s while the refusal guard and the health check both look fine.

  **Connect as `expense_engine`, not the owner.** The engine refuses to start as a SUPERUSER, which would bypass every RLS policy. `postgresql:///expense_world_test` connects as the owner and hits that guard.

  **The keys go on the command line, nowhere else.** The reseed prints two fresh PATs once, in its output (`scripts/practice-engine up` passes that output through): the shared practice user's, which goes in `EXPENSE_PAT`, and the reserved-names practice user's, which goes in `EXPENSE_RESERVED_PAT`. Read both there and pass them inline as `EXPENSE_PAT=<key> EXPENSE_RESERVED_PAT=<reserved key>` on the contract suite's own command line (below), never in a file (CLAUDE.md "Stay inside this repo"). The next reseed revokes both, so each is good for one check only.   **Pointing `expense` at it.** The app reads its key only from the file `EXPENSE_CONFIG` names ([expense/config.py](../expense/config.py)), so hand it the config as a pipe instead of a file: `EXPENSE_CONFIG=<(printf '{"engine_url":"http://127.0.0.1:8002","token":"<key>","main_currency":"PEN"}') expense …`. `main_currency` is there because a read of `/auth/me` otherwise saves it back into the config; anything that writes the config (the app's setup and Config screens, `import sheet --account-name` saving a rename) fails on a pipe. A pipe gives its contents to the first read only: `expense import sheet` reads the settings once, so it works this way, while the app reads them at launch and again for every engine call, so it does not.

  **Stop it when the check ends:** `scripts/practice-engine down`. By hand, only the tester may stop it: `kill <pid>` of the engine it started, or `lsof -ti :8002 | xargs kill` — the only stop forms the guard lets it run.

**Leftovers.** A contract test names what it builds `contract-…` (`freshman-…` in the freshman walk) and undoes it at teardown. Every test also fails, in its teardown, when it leaves an account, category or hashtag it made: `leaves_nothing` in [tests/contract/conftest.py](../tests/contract/conftest.py) lists them before the test and after every other fixture's cleanup, and names each one left by kind and name. It lists the shared practice user's always, and the reserved-names practice user's too for a test asking for `reserved_client`, naming a leftover there as that user's; a test that does not ask for it never needs `EXPENSE_RESERVED_PAT`. It does not count the system rows the engine creates for itself on first need and never deletes, the categories and hashtags with a `system_key` (`@Pendiente`, `@Opening` and the pending hashtag). [scripts/clean_practice_user.py](../scripts/clean_practice_user.py) removes such leftovers from the practice user through the engine's API: it matches accounts, categories and hashtags by those name prefixes, never a system row, takes a matched account's reconciliations and transactions with it (unarchive, revert, delete each statement once, delete the transactions, then the hashtags, categories and accounts), and leaves alone a card statement whose other half is on an account it does not match, a hashtag a live transaction still carries and anything the engine refuses to delete, listing each. It only reads unless given `--apply`, talks only to `:8002`, and takes the key only from `EXPENSE_PAT`: `EXPENSE_PAT=<key> python scripts/clean_practice_user.py --engine-url http://127.0.0.1:8002 --apply`. `--prefix P`, repeatable, matches names starting with `P` instead, for records a probe run by hand named its own way.

**Fixture drift.** The unit suite mocks the engine, so it cannot notice the engine changing shape. [scripts/check_fixture_drift.py](../scripts/check_fixture_drift.py) compares every unit fixture key against the engine's published `openapi.json`; run it after any engine change, against the `:8002` test engine above (its default target): `python scripts/check_fixture_drift.py --engine-url http://127.0.0.1:8002`. The flag stays explicit because the session guard ([.claude/hooks/guard.py](../.claude/hooks/guard.py)) blocks any run of the script without `--engine-url …:8002`. It is not a pytest file, to keep the unit suite hermetic. It checks two things. First, every quoted fixture key in `tests/unit` against the field and query-parameter names of the whole contract, so a key no endpoint serves is reported. Second, every fixture builder in [tests/unit/helpers.py](../tests/unit/helpers.py) marked with `answer_of(METHOD, PATH)` (they are listed in its `ANSWER_BUILDERS`): it calls each with no arguments and reports each field the contract marks required on that endpoint's answer that the result leaves out, inside nested objects and list items too, and reports an endpoint the contract no longer answers. A marked builder only spreads what a test passes over its bare answer, and asserts on every call that no key went missing. What it does not check: the first check reads only a key written in double quotes before a `:`, three characters or longer, so a key written as a keyword (`dict(amount_cents=…)`, a call's `note=…`) or a shorter one (`id`) passes unread; a key real on one endpoint passes the first check in every fixture; a marked answer's extra keys are not checked against its endpoint; a fixture no marked builder makes (a dict written in a test, `FakeClient`'s `{}` for a write with no default answer) is checked for neither; and a nested value a test passes in place of the bare answer's `None` is not checked. `FakeClient`'s default answers to a write (`FAKE_ANSWERS`) are built by marked builders, so the check covers their bare shape too; which writes have one: [tui.md](tui.md) §6.

**Contract version.** The same run compares the contract's `info.version` with the version saved in [scripts/engine-contract-version](../scripts/engine-contract-version), the version this repo was last checked against: one line holding the version and nothing else, never a copy of the contract. A different version is reported with both numbers (`saved …, engine …`) and fails the run even when every fixture key matches; a missing saved version fails it too. A moved version also prints what changed, read from the contract's own change log (`x-changelog` in `/openapi.json`, which the engine keeps newest first): every entry newer than the saved version, in that order, each as its version and date followed by every change as `kind: text` (the engine sends `kind` as `added`, `changed` or `removed`). It says the whole contract changed instead when the log is missing, empty or not a list, its first entry is not the engine's current version, the saved version is not in it, or an entry newer than the saved version is malformed; the saved entry and older ones are never read. A matching version prints nothing about the version or the log. A run never changes the saved version. Recording one is its own step, which writes the engine's current version and checks nothing else: `python scripts/check_fixture_drift.py --engine-url http://127.0.0.1:8002 --record-version`.

**Unit tests never touch the network.** `tests/unit/` is respx-mocked; autouse fixtures in [tests/unit/conftest.py](../tests/unit/conftest.py) redirect `EXPENSE_CONFIG` and block real sockets. Another pins the terminal every test sees to 80×24 (`COLUMNS` and `LINES`, `TERMINAL_SIZE` in that file), so Typer's output is the same in any window and in a pipe; TUI tests take their size from `run_test(size=…)`, never from the environment. Never bypass them.
