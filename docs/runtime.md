# Runtime Behavior

How the app (`expense`, the TUI) and the sheet import (`expense import sheet`) behave at runtime — read/write semantics, error handling, working against the live engine. Both are clients of the same HTTP client and `fetch_*` functions, so everything here applies to both. Companions: [tui.md](tui.md) (the app) and [commands.md](commands.md) (the sheet import and the settings file).

## Overview

The client holds no business logic and **no local state beyond `~/.expense-config`** — no cache, no offline write queue ([decisions.md](decisions.md) "All reads are live"). The engine is the only authoritative store and runs on the same machine (`http://127.0.0.1:8000`), so every read is a live loopback HTTP call.

## The settings file and a fresh start

The engine address and key live in the settings file, `~/.expense-config` (or the path `EXPENSE_CONFIG` names; its fields are in [commands.md](commands.md)). [expense/config.py](../expense/config.py) is its one reader and writer: `save` writes a temp file beside it, sets it to chmod 600 and moves it into place.

**A fresh start needs no command.** When the app opens with no settings file it can use — none at all, or one it cannot read for any reason (`config.load_usable`) — it opens on its setup screen, which asks for the engine address (offered as the local engine's, `http://127.0.0.1:8000`) and the key, and for a name when the engine has no profile for that key ([tui.md](tui.md) §2 "Setup comes first"). Nothing is written until the engine has accepted the address and key and the profile exists; then the file is saved, replacing a damaged one. `expense import sheet`, finding no usable file, stops on every step with a message pointing at the app's setup screen (exit 3).

## Read semantics

Every read is a direct `GET`. What a screen shows is what the engine computed at that moment, including home-currency figures (converted engine-side at read time).

- The engine's responses are IDs-only; the screens resolve names through live reference-list reads (`load_*_name_map` in [expense/reads.py](../expense/reads.py)), with a short-id fallback when one fails.
- **Deleted is deleted.** A deleted row is invisible to every client — no list returns it, its get is a 404 — and nothing in the app restores it. The engine keeps the row in its table; undeleting is an operator task outside the API (contract: "Base Conventions", "A delete is final"). The engine's activity history still holds a deleted row's history; this client has no screen for it.
- Transaction reads always send `debit_as_negative=true`, so the request pins the sign rather than depending on the engine default. The bank upload's rows and their days' unclaimed parts (contract: POST /v1/transactions/import) and a bank line's parts (contract: GET /v1/bank-lines/{bank_line_id}) arrive unsigned, as a magnitude and a `transaction_type`; `signed_cents` in [expense/formatting.py](../expense/formatting.py) signs them, the one place the app reads the sign off the type.

### Three list shapes

No list pages by position; every list is one of three shapes, each read its own way. The rules are the engine's (contract: "Base Conventions", "Lists come in three shapes, and none of them is paged by position"), with (contract: "Base Conventions", "Cursors, on every cursor-paged list") and (contract: "Base Conventions", "Date windows").

| Shape | Lists | How the app reads it |
|---|---|---|
| **Whole** `{items}` | accounts, categories, hashtags, a category's hashtags, an account's statements | One read, every row; no paging parameters. |
| **Cursor** `{items, limit, next_cursor}` | transactions, bank lines | `?after=<next_cursor>` until it is `null`. A count is its own read, `/transactions/count` or `/bank-lines/count` on the list's own filters, for the lists that show one. Which screen counts which list, and which reads every page rather than growing, is in [tui.md](tui.md), screen by screen; the growing lists are its §5. |
| **Cursor + date window** | activity, exchange-rate history | The cursor inside one window (30 calendar days counting `date_to`'s own day when `date_from` is left out; at most 366, counting both ends). The window before it is read by sending the response's `previous_date_to` back unchanged as `date_to`, which reads no row twice; `null` means nothing earlier. No screen reads these. |

A stale `limit`, `offset` or unknown parameter is the engine's `422`, never a quietly wrong answer.

## Write semantics

Writes go straight to the engine the moment you press enter. There is **no offline write queue, no buffering, no replay**.

- Each write carries an `X-Idempotency-Key` (UUID) minted once per logical write by `ExpenseClient`; the engine answers the same request sent again under the same key with its original response, so retrying is safe, and refuses the key sent with a different request (`409`).
- `ExpenseClient` ([expense/http.py](../expense/http.py)) retries a timed-out or 5xx write up to twice (1s/2s backoff) **with the same key** before surfacing the error, printing a stderr notice per attempt. Connect failures are not retried, and reads never auto-retry.
- Any other network error fails fast: the app shows it and the sheet import prints it and exits non-zero, so nothing assumes a write landed that did not.

**Bulk writes** — the LOG bar's save (`ctrl+s`) — go through one shared path, [expense/batch_write.py](../expense/batch_write.py), whose docstring gives its rules: rows go out in chunked `POST /transactions/batch` calls of 200 rows, under the engine's 500 (contract: POST /v1/transactions/batch), a refused send's unnamed rows go again, and a re-run after a half-written save writes nothing twice. **A refusal every further write would draw stops the run** (`errors.refuses_every_write`; [decisions.md](decisions.md) "Missing settings stop a multi-write run"): nothing more is sent, and the app says it once, on no row ([tui.md](tui.md) "Refused rows read one line per kind of error").

**How refused rows read** — under the LOG bar's table, in the ledger's bulk-edit toasts, and for the sheet import's refused rows, keyed by their spreadsheet row ([commands.md](commands.md) "A sheet with bad rows") — goes through one shared grouping, `grouped_refusals` in [expense/formatting.py](../expense/formatting.py): one line per kind of refusal, what was refused, then the rows it hit (`row 77`, or `rows 3, 5, 7`). A row the engine names shows each refused field as the engine keys it, minus the row's place in the request, then the engine's words for it (`errors.row_words`); two fields join with ` · ` (`amount_cents: Must not be zero. · date: Must not be null.`), and a refusal naming no field shows its message. Rows refused alike share one line, whichever send of the run refused them: alike is the same code, fields and reasons (`errors.refusal_kind`, which `BatchFailure.kind` reads), never the top-level message, which counts the items a send named. A refusal naming no row is a line of its own: the engine's words whole, the rows it covers after its first line, its field lines under it. What each surface adds: [tui.md](tui.md) "Refused rows read one line per kind of error".

## Engine errors surface cleanly

The engine's `{ error: { code, message, fields, reasons } }` envelope is rendered intact. `EngineError` ([expense/errors.py](../expense/errors.py)) keeps `reasons` — each refused field's reason code (contract: "Error reasons"), `None` when the engine sends it null or leaves it out — for code to decide on. The app may add a line for a known refusal without replacing the engine's message; it is chosen by the error code and the reason code, never by the route or the wording of `message` or `fields` ([decisions.md](decisions.md) "Hints are chosen by the engine's reasons, never its wording"). Which refusals get a line, and the lines themselves, are listed in [tui.md](tui.md) "When the engine says no". The sheet import adds none; how it prints an error, and its `--json`, are [commands.md](commands.md) "Output conventions".

Two hints belong to no single screen and live in the shared error text, `format_error` in [expense/errors.py](../expense/errors.py), which the TUI's toasts and banners print after a blank line under the engine's code, message and fields; the TUI bank import shows them in its toast, its on-screen refusal being the code, the message and a line per refused key ([tui.md](tui.md) "The import door"):

- **A `401`** — the key is missing or not valid: `Hint: the key is missing or not valid. Set a fresh one on System ▸ Config (press t).`
- **`SETTINGS_MISSING`** — the user's settings do not exist yet (contract: "Error codes"). Matched on the error code alone: `Hint: First-time setup is not done yet. Open System ▸ Auth & profile and press b.`

Every remedy the shared text gives points at a screen of the app, never at a typed command (guard: `test_no_message_in_the_app_tells_the_owner_to_type_a_command` in [tests/unit/test_tui_setup.py](../tests/unit/test_tui_setup.py)). The TUI's launch-time rate check shows nothing on any engine error, this one included.

## Working against the live engine

There is exactly **one engine: the local deployment** (`http://127.0.0.1:8000`, launchd service on the owner's Mac, set up by the engine's local-deployment guide). No staging, no sandbox — every PAT belongs to a real user and every write lands in the one true ledger, a plain `expense` included ([CLAUDE.md](../CLAUDE.md) "Careful running live").

**Isolation levers, weakest to strongest:**

- `EXPENSE_CONFIG` redirects the config file. This isolates *local config only* — the same PAT still writes to the same ledger.
- A **separate PAT for a separate user** is data isolation within the same database (PATs: [commands.md](commands.md) "Auth model").
- **A second engine over the `expense_world_test` database** — how the contract suite runs. Nothing it writes can reach the real ledger.

  **Start and stop it with one command, from this repo:** `scripts/practice-engine up` and `scripts/practice-engine down` ([scripts/practice-engine](../scripts/practice-engine); its header says how it keeps the caller's environment out). Every agent may run them; the orchestrator does, before and after a task that needs the contract live. `up` starts the engine with the engine's own practice launcher, `deploy/local/client-practice-engine.sh 8002`, run detached from the engine checkout's root (or reuses the one already on `:8002`), waits for `/health`, reseeds the two practice users and prints their fresh keys to the terminal. The launcher serves an export of the engine's last commit, never the checkout's uncommitted work, over `expense_world_test` on `127.0.0.1:8002`, and names that commit in its log (`/tmp/expense-test-engine.log`). A reused engine keeps the commit it started on, so after a new engine commit, `down` then `up` serves it. `down` stops by its pid only a practice engine: whatever listens on `:8002` when its command line ends in the launcher's engine start (`-m uvicorn app.main:app --host 127.0.0.1 --port 8002`) and its working folder is the launcher's export, whoever started it. The session guard ([.claude/hooks/guard.py](../.claude/hooks/guard.py)) lets a command naming the script through only in the exact shapes its docstring lists, so its output, which carries both keys, reaches only the terminal ([decisions.md](decisions.md) "The practice engine has one script, run in exact shapes").

  **The practice users.** In the engine repo, `deploy/local/seed-test-user.sh` seeds two practice users, a PAT for each and a copy of `exchange_rates`. The **shared practice user** is the one every contract test writes as. The **reserved-names practice user** owns categories named `@Pendiente` and `@Opening` and a hashtag named `Pendiente`, so a test can draw the engine's refusal of a reserved name as that user. Run with `--force`, it reseeds: it revokes every PAT each practice user holds, prints one fresh one per user, each under its user's heading (`shared practice user (<id>):`, then `reserved-names practice user (<id>):`), and refreshes the copy of `exchange_rates`; each practice user's id and every row it holds stay, so a test cleans up the rows it makes and never assumes a practice user starts empty.

  **By hand, only the tester** starts it, with the launcher alone, run from the root of the engine checkout, `expense_world_engine`, beside this repo ([README](../README.md) "Checkout layout"):

      nohup deploy/local/client-practice-engine.sh 8002 > /tmp/expense-test-engine.log 2>&1 < /dev/null &

  The launcher takes `8002` as its one argument and fixes the database and the interpreter itself, so the start takes no environment; `nohup`, the redirects and the `&` keep it running after the agent that started it finishes (started as an agent's own background task instead, it stops with that agent). The guard refuses every other start, since an engine run by hand serves the checkout's uncommitted work. At the start of each check the tester reseeds by running `deploy/local/seed-test-user.sh --force`, from the same folder (the engine checkout's root). It stops only the engine it started: `kill <pid>`, or `lsof -ti :8002 | xargs kill`.

  **Port 8002, not 8001.** `:8001` is `todo_world_engine`'s — point the suite there and every request 404s while the refusal guard and the health check both look fine.

  **The keys go on the command line, nowhere else.** The shared practice user's key goes in `EXPENSE_PAT`, the reserved-names practice user's in `EXPENSE_RESERVED_PAT`, both inline on the command that uses them (below), never in a file ([CLAUDE.md](../CLAUDE.md) "Stay inside this repo"); the guard keeps the seed's and the script's output off disk. The next reseed revokes both, so each is good for one check only.

  **Pointing `expense` at it.** The app reads its key only from the file `EXPENSE_CONFIG` names ([expense/config.py](../expense/config.py)), so hand it the config as a pipe instead of a file: `EXPENSE_CONFIG=<(printf '{"engine_url":"http://127.0.0.1:8002","token":"<key>","main_currency":"PEN"}') expense …`. `main_currency` is there because a read of `/auth/me` otherwise saves it back into the config; anything that writes the config (the app's setup and Config screens, `import sheet --account-name` saving a rename) fails on a pipe. A pipe gives its contents to the first read only: `expense import sheet` reads the settings once, so it works this way, while the app reads them at launch and again for every engine call, so it does not.

  **Stop it when the check ends:** `scripts/practice-engine down`.

**The contract suite** (`tests/contract/`) hits a real engine and is double-gated: `PYTEST_LIVE=1 EXPENSE_PAT=<key> EXPENSE_RESERVED_PAT=<reserved key> EXPENSE_ENGINE_URL=http://127.0.0.1:8002 pytest tests/contract`, `<key>` and `<reserved key>` being the two the last reseed printed. `EXPENSE_ENGINE_URL` names the target; its default is the live `http://127.0.0.1:8000`, so always set it to the `:8002` test engine (the session guard refuses a contract run without it). A test that writes as the reserved-names practice user asks for `reserved_client` ([tests/contract/conftest.py](../tests/contract/conftest.py)); without `EXPENSE_RESERVED_PAT` that test fails, naming the variable, rather than skipping. Without `EXPENSE_PAT` the suite refuses to start on the developer's own config ([decisions.md](decisions.md) "Contract tests verify against a disposable database"); `EXPENSE_ALLOW_REAL_LEDGER=1` overrides it. It runs in one process: [tests/contract/conftest.py](../tests/contract/conftest.py) turns `-n auto` into zero workers, and [tests/conftest.py](../tests/conftest.py) does the same for any live run started above it, such as a bare `pytest`; only an explicit `-n N` overrides them ([decisions.md](decisions.md) "Live contract runs stay in one process").

**What it pins:** each file in `tests/contract/` says so in its docstring. Every test calls the engine through the app's own HTTP client and walks real flows; `test_contract_citations.py` checks every `(contract: …)` citation in the repo against the live contract. A test builds what it needs through `Scratch` in [tests/contract/conftest.py](../tests/contract/conftest.py) (`row_at` and its kin make transactions, `body` and `opening_balance_body` build the bodies a test sends itself), which undoes it best-effort in reverse dependency order. Cleanup means **soft-deletes** — invisible to every client but still in the database — which is why it belongs on the practice database. Run it when engine-shape drift is suspected or before calling a release done; never in CI. It catches what mocks cannot, e.g. `amount_cents` returning as a magnitude unless the read asks for `debit_as_negative`.

**Leftovers.** A contract test names what it builds `contract-…` (`freshman-…` in the freshman walk) and undoes it at teardown. Every test also fails, in its teardown, when it leaves an account, category or hashtag it made (`leaves_nothing` in [tests/contract/conftest.py](../tests/contract/conftest.py)), on the shared practice user and, for a test asking for `reserved_client`, on the reserved-names one; a test that does not ask for it never needs `EXPENSE_RESERVED_PAT`. [scripts/clean_practice_user.py](../scripts/clean_practice_user.py) removes such leftovers through the engine's API; its docstring says what it matches and the order it deletes in. It only reads unless given `--apply`, talks only to `:8002`, and takes the key only from `EXPENSE_PAT`: `EXPENSE_PAT=<key> python scripts/clean_practice_user.py --engine-url http://127.0.0.1:8002 --apply`. A leftover on the reserved-names practice user is cleaned by passing that user's key as `EXPENSE_PAT`. `--prefix P`, repeatable, matches names starting with `P` instead, for records a probe run by hand named its own way.

**Fixture drift.** The unit suite mocks the engine, so it cannot notice the engine changing shape. [scripts/check_fixture_drift.py](../scripts/check_fixture_drift.py) checks the unit fixtures against the engine's published `openapi.json`: every quoted fixture key in `tests/unit` (`KEY_RE`) against the field and query-parameter names of the whole contract, and every fixture builder in [tests/unit/helpers.py](../tests/unit/helpers.py) marked `answer_of(METHOD, PATH)` (listed in its `ANSWER_BUILDERS`) for each field the contract requires on that endpoint's answer. Run it after any engine change, against the `:8002` test engine: `python scripts/check_fixture_drift.py --engine-url http://127.0.0.1:8002` (the session guard blocks a run without that flag). It is not a pytest file, to keep the unit suite hermetic. What it cannot see is its docstring's KNOWN LIMITATION. `FakeClient`'s default answers to a write (`FAKE_ANSWERS`) are built by marked builders; which writes have one: [tui.md](tui.md) §6.

**Contract version.** The same run compares the contract's `info.version` with the version saved in [scripts/engine-contract-version](../scripts/engine-contract-version), the version this repo was last checked against: one line holding the version and nothing else, never a copy of the contract. A different version is reported with both numbers (`saved …, engine …`) and fails the run even when every fixture key matches; a missing saved version fails it too. A moved version also prints what changed, read from the contract's own change log (`x-changelog` in `/openapi.json`, newest first): every entry newer than the saved version, in that order, each as its version and date followed by every change as `kind: text` (`added`, `changed` or `removed`). It says the whole contract changed instead when the log is missing or malformed, its first entry is not the engine's current version, or the saved version is not in it. A matching version prints nothing about the version or the log. A run never changes the saved version. Recording one is its own step: `python scripts/check_fixture_drift.py --engine-url http://127.0.0.1:8002 --record-version` writes the engine's current version only when the change log lists it, since an engine running unreleased work serves draft versions the log never lists (contract: "Base Conventions", "The contract"); otherwise it records nothing, exits 1 and says the served version may be a draft. A missing or malformed log lists nothing.

**Unit tests never touch the network.** Autouse fixtures in [tests/unit/conftest.py](../tests/unit/conftest.py) block real sockets, redirect `EXPENSE_CONFIG` and pin every test's terminal to 80×24 (`TERMINAL_SIZE`), so Typer's output is the same in any window and in a pipe; TUI tests take their size from `run_test(size=…)`, never from the environment.
