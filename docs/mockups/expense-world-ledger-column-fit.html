Transactions — cells that fill their columns

The ask, 2026-09-12, verbatim: “Look at the expense world TUI, the columns are wide but the content gets trucated, they should match the size.”

Nothing is built. Pick one and it gets built; that is the rule in CLAUDE.md (“Mock every screen before building it”) and showing is not approval.

Provenance. Every row on this page is real — the newest 14 rows of your live ledger on 2026-09-12 (the September bank import, still @Pendiente), and for the page-turn frames the rows at offset 150. The frames are character-exact: each one is Rich drawing the same Table that CursorList._build draws, with the column policy swapped, so the widths you see are the widths the terminal draws. Drawn at 160 columns (about your terminal) and again at 80, the size the screens were designed at. The third row is the cursor.

1 · Why it happens

Three lines of transactions.py, one cause. transaction_rows cuts every cell before the table exists: truncate(title, 20), truncate(description, 18), format_hashtag_cell(…, max_width=20). The CursorList table is expand=True, so it then stretches to fill the card — Rich hands the slack to each column in proportion to what it measured, and what it measured was the already-cut text. The column grows; the ellipsis stays where the 20-character cap put it. Your titles run to 39 characters (ANTHROPIC* CLAUDE SUB  ANTHROPIC.COM CA) and so do your descriptions; the caps were sized for an 80-column card that this screen stopped using on 2026-08-29, when Transactions became the one screen that fills the window.

2 · Option A — flex columns recommended

Drop the three caps; the row builder hands the table the whole string. Then tell the table which columns are free text: Title, Description and Hashtags get a Rich ratio (3 : 3 : 2), the other four keep their natural width. Rich takes Amount, Date, Account and Cat at their measured size first and splits everything left between the three text columns by ratio; each cell is then cut by the table itself, at the edge of the column it actually has (no_wrap is already set, and Rich’s overflow is already ellipsis). One new CursorList parameter, flex={0: 3, 1: 3, 6: 2}, used by this screen only.
Why this one: the text columns are exactly as wide as the terminal allows and the cut lands at the column edge — what you asked for — and the column edges do not move when you page: a page with a 39-character description gets the same layout as a page without one. On a narrow terminal the free text gives way first and the numbers, dates and names stay whole, which is the order a ledger should degrade in.
The cost: at 80 columns the text columns are very short (Title 6 characters, Description 5, see §4); today they are 15 and 14 there, but today’s amount is -16… and its date 2026-…. The ratios are numbers you can pick.

3 · Option B — natural width

Drop the three caps and change nothing else. Rich measures the longest cell in each column on this page, and because the table still expands, spreads the slack in proportion to those measurements. The smallest diff — three arguments removed.
The cost, twice: the layout is data-dependent. Column edges jump on every page turn, because each page has a different longest title and description (compare the two frames below: Description is 47 wide on page 1 and 25 wide at offset 150; Title goes from 29 to 37). And when a page carries a long description on a narrow terminal, Rich’s last resort trims every column by the same amount, so the 9-character amount pays as much as the 39-character description — at 80 columns Amount is a bare …, Date is 2… and the Hashtags column is gone altogether (§4).

6 · The pick

A or B. If A, the ratios 3 : 3 : 2 are a proposal — say if you want Title or Description to take more of the width, or Hashtags less. Untouched either way: the seven-column set, the row order, the LOG bar’s account peek (its own 28-character cap, a fixed-width surface), and the flat expense transactions list table.
