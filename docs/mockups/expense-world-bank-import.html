Bank Import

You hand the app a bank download; the app asks which account it belongs to, shows you what it would write and what it already has, and on --apply writes only the new rows — under @Pendiente, ready for the categorising pass. Duplicates are found by matching against the ledger, not by hashing the file: the bank's operation number when it has one, and otherwise date, amount, account and title with a one-day tolerance and a count per group.

Drawn from the two real downloads in ~/Downloads on 2026-09-12: Sueldo Soles.xlsx (20 rows, carries an operation number) and VISA Infinite Sapphire.xlsx (80 rows, mixed S/ and $, no operation number).

Your calls, 2026-09-12

  • The app asks which account. A card with two currencies is one pick; the currency column chooses the leg per row (S/ → BCP Signature PEN, $ → BCP Signature USD).
  • The operation number is the duplicate resolver when the file has one. Without it: date ± 1 day, amount and account, with a count per group — three rows of 3.50 in the file mean at most three in the ledger.
  • Card descriptions are cleaned: the merchant part only, whitespace collapsed; the raw text is kept in the description field.
  • The operation code becomes a column on every transaction, unique per account at the database.

Two things this mockup leaves for you to pick

  • Pane 1 — ask which account every time (A), or remember the file name → account choice in your config after the first run (B).
  • Pane 5 — when the ledger holds more rows in a group than the file does, the preview says so. Whether that is a dim note or a loud one is a taste call.
1 · the command, and the account it asks for

One argument, the file. The sheet is read, the currencies it holds are counted, and the account list is shown with cards folded into one entry per name — a two-leg card is one answer. Picking a single-currency account for a file that holds both currencies is refused before anything else happens.

B is the recommendation, because the file name is the bank's and it does not change between downloads; the remembered pair lives in ~/.expense-config beside the engine URL. A is what the first run of any new file does under B anyway.

4 · --apply

One POST /transactions/batch for the new rows, the same shared writer the LOG bar and expense import use. A row the engine refuses is named by number with the engine's own message. The last line points at the next job.

zsh
$ expense import bank ~/Downloads/"VISA Infinite Sapphire.xlsx" --apply
  Account: BCP Signature (remembered)
  80 rows · 63 new · 17 in the ledger · 0 refused

  63 written · 58 → BCP Signature PEN · 5 → BCP Signature USD · all under @Pendiente
  Categorise them: expense world → Transactions → p
5 · when the ledger has more than the file

A group where the ledger holds three and the file holds two is not an insert — it is a hint that something was logged twice before. The preview says so and writes nothing for that group. Two weights to choose from.

C · a dim note

zsh
  80 rows  63 new  ·  17 in the ledger  ·  0 refused
  1 group has more in the ledger than in the file:
    2026-09-07 · -3.50 · BCP Signature PEN — ledger 3, file 2

D · a loud one

zsh
  80 rows  63 new  ·  17 in the ledger  ·  0 refused
  ! 1 group has more in the ledger than in the file — a row may be logged twice
      2026-09-07 · -3.50 · BCP Signature PEN — ledger 3, file 2
    expense transactions list --account-id … --from 2026-09-06 --to 2026-09-08

D is the recommendation. The one thing the count rule can detect that nothing else can is an earlier double entry, and a hint you can miss is a hint you will.

6 · refusals

A row the importer cannot place is listed and skipped; the rest of the file still previews. Refusals never write, and they never guess.

zsh
$ expense import bank ~/Downloads/"VISA Infinite Sapphire.xlsx" --account "BCP PEN"
  ! BCP PEN holds PEN only, and this file has 7 rows in USD. Pick the card (BCP Signature), or a USD account.

$ expense import bank ~/Downloads/"Sueldo Soles.xlsx"

    row 15: "31/13/2026" is not a date
rules · how a file row is matched, in order — each ledger row is claimed at most once
1 · operation codeBoth sides carry one → exact match on account + code. The other rules are skipped for that row, matched or not. Sueldo Soles rows always take this path from the second download on.
2 · same day + titleSame account, same date, same amount, same cleaned title. Catches rows the old sheet imported and rows an earlier download wrote.
3 · ±1 day + titleAs 2, but the ledger row may sit one day either side — the pending-to-posted shift on a card.
4 · ±1 day, amount onlySame account and amount within a day, title ignored: your count rule. Catches rows typed in the LOG bar under your own title. Exact-date candidates are claimed before neighbours, so a file row on Tuesday prefers Tuesday's ledger row over Monday's.
count per groupRules 2–4 are run row by row, and because each ledger row is claimed once, a group of three identical file rows against one ledger row leaves two unmatched → two new. That is the count, without a separate counting step.
what is writtenUnmatched rows, as a batch: date, amount, account leg, cleaned title, the raw description as description, the operation code when present, no category (the engine files them under @Pendiente), no hashtags. Fresh ids — idempotency comes from the match, not the id.
what the engine gainsoperation_code, nullable text, on POST/PUT/batch and every transaction response, with a partial UNIQUE index on (user, account, code) — the hard floor under rule 1.
the honest limitA card row that moves by more than a day between downloads, or changes amount (a tip added at settlement), is not matched and imports twice. The unreconciled check over the statement period remains the backstop.
title cleaning · merchant only, raw text kept
raw (card)LIDERMAN OUTLET AREQUI ICA PE — the bank pads the merchant to 22 characters, then city, then country.
titleLIDERMAN OUTLET AREQUI — the first 22 characters, trimmed, inner runs of spaces collapsed.
descriptionthe raw cell, verbatim — so nothing the bank said is lost, and a search for the city still finds it.
current accountTRAN.CEL.BM., EDIF000000000605 — no padding, no suffix; the same cleaner leaves them untouched.
rejected · the ones that needed more than a line

Content-hashed ids (the old importer's scheme, minus the row number).

Deterministic and no ledger read — and blind to everything this flow actually meets: the August rows the old sheet already imported under positional ids, the rows you typed in the LOG bar under your own title, and a card row whose date moves a day between downloads. Every one of those becomes a duplicate. Matching against the ledger sees all three.

Date + amount + account only, no title anywhere in the chain.

Two rides at the same fare on the same day would be one match and one silent loss. Title stays as rules 2 and 3 before the amount-only rule 4, so identical merchants match first and only the leftover falls through to the count.

A per-bank parser (a "BCP module").

Both files already share one shape — Fecha, Descripcion, Moneda, Monto, and an optional Numero de Operacion — under two date spellings. One tolerant column mapping covers both, the way expense import already tolerates header spellings. A bank module is what to build the day a second bank's export looks different.
