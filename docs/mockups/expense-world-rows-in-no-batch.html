Corrected 2026-09-22. The first draft of this file sent you to the ledger with a filter. Wrong: reconciliation work stays in the reconciliation view. Nothing here pushes the ledger, and nothing here needs Home.

Two places, two different questions — §1 "what is unfiled on this account, ever?" on the account screen, and §3 "what is blocking this close?", which turns out to need almost nothing new. Everything in yellow is new; the rest is on screen today, drawn from the code.

  • The pane swaps, the screen does not. Same two-pane screen, same account cursor on top — only the lower list changes what it is listing. esc swaps it back.
  • Why the account screen and not the batch screen: the rows that matter most are dated in months that have no batch, or months whose batch is long closed. They do not belong to any one batch, so they cannot live on one batch's screen.

No explanatory line — the date column says it (your call, 2026-09-22). What the dates alone cannot say is which rows land inside a batch you already have, so those carry !: the three August rows sit inside August 2026 (07-24 → 08-25) and will refuse its close until you tick them or fix them. February, March and the July row are in months with no batch at all — untidy, not blocking.

One honesty note on the !: it is drawn by comparing each row's date against this account's batch windows, which the screen already holds — a hint, not a ruling. The engine stays the authority at close time, so a flag can be one day off at a window edge without anything downstream believing it.

3 · A refused close — no new view, it points at u

Nothing is built for this (your call, 2026-09-22). The refusal says what happened and where to look: esc back to the account, press the key, and the blocking rows are the ones carrying !. The same list you would have opened anyway, so there is no second way to see the same rows.

The unticked rows on the batch screen are those same rows, since the checklist already holds the account's unfiled rows inside the window — so you can also just tick them here without going anywhere. What the refusal must not do is tick them for you.

4 · The leftover: a bulk move the ledger refused

One piece of ask 1 is genuinely not reconciliation work and cannot move here: in the ledger, selecting rows and pressing b to move them to another account can be refused by a closed period on the destination. Today that is one ten-second toast per row — eight refusals, eight stacked toasts.

Since you are standing in the ledger when it happens, the cheap fix is one summary toast naming the periods, with the refused rows staying selected so the same key retries exactly them. No screen, nothing new to learn.

What I need you to pick

1 · The key letter for the pane swap

n is taken (new batch), r is refresh. I drew u, but on the batch screen one keypress away u means revert — the "one key per job" rule warns about exactly that. Free: o (orphans), f, x. Or keep u and accept the overlap.

2 · Does d go in, with no undo inside the TUI?

Cursor row only, one confirm, never a selection. Yes as drawn; no leaves deleting to the typed side; or yes, and a restore door later — the engine has one, nothing in the TUI uses it.

3 · An explanatory line about closed statements — answered: no (2026-09-22)

"I can see myself by the date column." The line is gone. What replaced it is the ! flag, which marks something the dates alone do not carry: the row lands inside a batch that already exists on this account, so it will refuse that batch's close.

4 · §4, the summary toast — answered: yes (2026-09-22)

One toast naming the periods, refused rows staying selected, eight-toast pile-up gone. The only piece of this ask that stays in the ledger, because that is where it happens.
